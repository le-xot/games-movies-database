# 0002 — Lifecycle-реестр вместо ручных списков `started`/`stoppable`

## Контекст

Nest-эпоха оставила хуки `onModuleInit` / `onApplicationBootstrap` /
`onModuleDestroy`, но вызывал их composition root по двум ручным спискам. Списки
разъехались с реальностью: `DrizzleService` не получал ни ping при старте, ни
`pool.end()` (его звали вручную в `close()`), таймер погоды не снимался, а
`CocktailBotService` создавался ради побочного эффекта и не отслеживался.

## Решение

`server/lifecycle.ts` — реестр `Lifecycle.add(service)`: сервис регистрируется там
же, где создаётся (`lifecycle.add(new X(...))`), поэтому «забыли добавить в
список» невозможно. Хуки вызываются в порядке регистрации, ошибка логируется и не
отменяет остальные. `container.init()` / `container.close()` делегируют реестру.

## Альтернативы

1. **Оставить списки и добавить dev-assert.** Ловит забытый сервис только при
   запуске приложения, а не в тестах; список всё равно нужно править руками.
2. **Автоматический DI-контейнер.** Для 29 сервисов с явными конструкторами это
   больше инфраструктуры, чем экономии; проект сознательно живёт без DI.

## Последствия

- Порядок хуков изменился на порядок создания (`drizzle → weather → twitch → …
  → telegramBot → miniApp → notifications`). Безопасность проверена в ревью:
  команды ботов регистрируются в конструкторах до `init()`.
- `DrizzleService.onModuleInit` (ping) теперь реально вызывается; в ревью отмечено,
  что ping без таймаута может замедлить старт при мёртвой БД, но старт не падает.
- Ловушки: `server/__tests__/lifecycle.spec.ts` (порядок, `this`-биндинг,
  изоляция ошибок) и руководство в `server/AGENTS.md` / `docs/architecture.md`.
