# 0003 — Ключ лимита из `ctx.route`, а не из имени Nest-контроллера

## Контекст

Каждый роут-плагин копировал замыкание над `enforceRateLimit`, а ключ окна был
зашит строкой вида `RecordController.getAllRecords` — имена контроллеров, которых
нет с 2024 года. Переименование роута не меняло ключ, ключи расходились с
реальными путями, а 72 вызова были размазаны по 19 файлам двумя разными
сигнатурами.

## Решение

`gateway/rate-limit.ts` экспортирует `rateLimitGuard(limiter, defaultConfig?)`.
Ключ вычисляется из контекста: `rl:{request.method} {ctx.route || pathname}:{ip}`.
`ctx.route` — путь, зарегистрированный в роутере (`/records/:id`), поэтому
параметры не попадают в ключ и лимит нельзя обойти перебором id.

## Альтернативы

1. **Оставить строковые ключи, вынеся только замыкание.** Меньше правок, но
   legacy-имена и риск расхождения остаются.
2. **Считать ключ по URL (`request.url`).** Отклонено: `/records/1` и `/records/2`
   получают разные окна — лимит обходится.

## Последствия

- Удалены ~50 строк-ключей; 9 closure + 15 прямых вызовов → 19 фабрик / 72 вызова.
- Прежние окна в Redis сбрасываются один раз при деплое — окна эфемерны, это
  ожидаемо; пресеты у всех 72 роутов сверены 1:1 в ревью.
- Ловушка: `gateway/__tests__/rate-limit-guard.spec.ts` — параметры не дробят
  ключ, методы/пути различаются, query игнорируется, fallback на pathname.
