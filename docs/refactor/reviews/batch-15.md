### Блокер

**B1. `NOTINTERESTED`: бейдж без фона стал залитым `bg-[#4a4a4a]` — видимое изменение UI.**

- Родитель: `5147b6b:frontend/src/components/media/badge/composables/use-badge-select.ts` — у `NOTINTERESTED` только
  `name` и `description`, ключа `class` нет (проверено и по истории: с коммита `7ec78ee`, где бейджи переехали в
  `statusTags`, класс у статуса отсутствовал всегда). HEAD: `frontend/src/lib/record-vocabulary.ts:54-58` —
  `tone: '#4a4a4a'`, `badgeClass: 'bg-[#4a4a4a]'`.
- Как это рендерится: `BadgePopover.vue:57,79,91,115` — `:class="data.tag?.class ?? 'border border-input'"`.
  Было: `class` отсутствует → fallback `border border-input` (прозрачный фон, 1px контур; dark `--input` =
  `oklch(26.9% 0 0)`). Стало: `bg-[#4a4a4a]`, без контура. То же в фильтре: `FilterStatus.vue:17-20` передаёт
  `class: optionClass` в `FilterPopover.vue` (базовая кнопка `border` + класс опции) — раньше опция была
  контурной, теперь залита. Затронуты все пользователи, не только админ: в `MediaCard` бейдж рисуется и без
  popover'а (ветка `v-else`), в двух местах карточки (`MediaCard.vue:223-229`, `:266-271`).
- Проверено статическим рендером на собранном CSS (`dist/assets/index-*.css`, dark-тема, те же базовые классы и
  fallback'и, что в компонентах): слева — прозрачная «капсула» с контуром, справа — серый заполненный бейдж.
  Разница видна отчётливо; у `QUEUE` (`bg-[#333333]`) до/после одинаково. Для справки: литерала `bg-[#4a4a4a]`
  в исходниках родителя нет (`git grep` по `5147b6b` — 0 совпадений), а в собранном HEAD он есть — Tailwind
  подхватил новый литерал, то есть изменение действительно доезжает до продакшена.
- Почему это не «мелочь»: кампания — не редизайн, и предыдущие ревью принимали схлопывание бейджей именно как
  «замену точную» (`batch-01`). Смена вида бейджа — продуктовое решение, а не следствие канонизации; в
  `tasks.md` открытый вопрос №2 фиксирует, что даже скрытие `NOTINTERESTED` из статистики не подтверждено
  владельцем — тем более нельзя молча менять его бейдж.
- Причина структурная: `RecordVocabularyEntry.badgeClass` обязателен (`record-vocabulary.ts:19`) и
  `record-vocabulary.spec.ts:24-32` требует, чтобы `badgeClass` содержал `[${tone}]`, — поэтому «оставить без
  класса» новая канонизация выразить не может. Это и есть скрытый UX-дрейф в типе.
- Как починить (сохранив UX попиксельно): сделать `badgeClass` необязательным (или разрешить `null`) и в
  `toBadgeTags` передавать `class: entry.badgeClass` как есть — тогда `undefined` снова уходит в fallback
  `BadgePopover`, а `FilterStatus` получает опцию без класса, как раньше; тест «tone ↔ class» проверять только
  при наличии `badgeClass` (`badgeClass?: string`, `if (entry.badgeClass) { … }`). `tone: '#4a4a4a'` остаётся для
  `STATUS_COLORS` — статистика не меняется. Альтернатива: владелец явно подтверждает выравнивание бейджа
  (тогда это отдельное продуктовое решение — фиксируется в журнале/в сообщении коммита, и блокер снимается).
